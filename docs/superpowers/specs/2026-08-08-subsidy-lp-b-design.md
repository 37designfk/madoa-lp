# 補助金LP B案 設計書

作成: 2026-08-08

## 背景と目的

現行の補助金LP（`/subsidy/`）は、広告経由モバイルの平均滞在が10.6秒・直帰率90%で、
実ユーザーのCVを1件も確認できていない（`docs/tracking.md`「CTAタップ停止の調査結果」参照）。

デスクトップは同じ広告・同じLPで平均124秒読んでいる。モバイル固有の問題であり、
広告流入の95%がモバイルなので、これが全体を決めている。画像圧縮で1.9秒→10.6秒まで改善したが、
直帰率90%は動いていない。次に疑うべきはファーストビューの中身、という結論で調査が終わっている。

あわせて、リフォームには6つの購入抵抗がある。

1. 自分の家が補助金の対象か分からない
2. いくらかかるか見当がつかない
3. 問い合わせたら営業されそう
4. 工事が大掛かりで面倒そう
5. 補助金の申請手続きが煩雑そう
6. どの業者が信用できるか分からない

現行LPは6と2に部分的に答えているが、1・3・4・5への答えが弱い。特に1は補助金LPの核心なのに
ファーストビュー直下にない。

B案の目的は、**10秒で帰るモバイルユーザーに「読ませる」のではなく「操作させる」**ことで
離脱前に自分ごと化させ、その過程で6つの抵抗を潰すこと。

## 決定事項

| 論点 | 決定 |
|---|---|
| 基本方針 | 診断ファースト型。FV直下に3問の対象判定を置く |
| 金額の開示 | 自己負担額の目安まで出す。ただし施工価格が未確定のため、初期リリースはフラグでオフ |
| A/B運用 | B案に切り替えて前後比較。A案（`/subsidy/`）は削除せず残す |
| 受け皿 | LINE中心。診断結果はコピーボタンで渡す。フォームは作らない |
| 実装方式 | 素のJS＋単一Astroコンポーネント。React等の依存は追加しない |
| 素材 | 新規撮影なし。既存の `public/images/subsidy/` で組む |

### 実装方式を素のJSにした理由

状態は「3問の回答＋現在の画面」だけで、React等を入れる規模ではない。
主戦場がモバイル速度である以上、ランタイムJSを増やすのは目的に反する。
既存プロジェクトは Astro の静的出力だけで完結しており、その構成を崩さないのが最も安全。

## URL とページ構成

- パス: `/subsidy-b/`
- `noindex`: **必須**。現行 `/subsidy/` と内容が重複するため、検索エンジンに両方出さない。
  `Layout.astro` の `noindex` プロパティを使う
- `variant`: `line`（ヘッダーのCTAをLINEにする）

### 計測上の注意

既存のカスタムコンバージョン `LINEクリック_補助金LP` / `電話クリック_補助金LP` は
URL contains `lp.madoa.co.jp/subsidy` で判定している。`/subsidy-b/` もこの条件に**マッチしてしまう**ため、
A案とB案のCVが合算される。

前後比較で運用するので合算でも判定はできるが、切り分けたいなら
B案専用のカスタムコンバージョンを2件追加する（URL contains `lp.madoa.co.jp/subsidy-b`）。
`docs/tracking.md` の検証でパス条件が機能することは確定済み。

## セクション構成

上から順に。括弧内は潰す抵抗の番号。

| # | セクション | 内容 | 抵抗 |
|---|---|---|---|
| 1 | StickyBar | モバイル下部固定。診断前は「30秒で対象チェック」、診断後はLINE/電話に切り替え | - |
| 2 | Hero | 見出し1行＋診断開始ボタン。文字量は現行の半分以下 | 1 |
| 3 | Diagnosis | 3問の診断ウィジェット＋結果表示 | 1, 2 |
| 4 | NoSales | 営業しません宣言 | 3 |
| 5 | WorkReality | 工事のリアル（所要時間・片付け不要・養生） | 4 |
| 6 | Paperwork | 申請手続きの分担表 | 5 |
| 7 | Pricing | 補助金額表（現行の数字をそのまま使う） | 2 |
| 8 | Trust | 会社の信頼（創業年数・施工実績・対応エリア） | 6 |
| 9 | Cases / Testimonials | 既存コンポーネントを再利用 | 6 |
| 10 | Faq | 6つの抵抗に対応したFAQ | 全部 |
| 11 | Cta | 最終CTA | - |

現行LPとの最大の違いは、2と3で**ページに入って最初の1画面が診断**になっていること。
現行は Hero に文字と写真とバッジが詰まっており、モバイルで読み切る前に離脱している。

## 診断ウィジェットの設計

### 質問

3問。すべて選択式で、テキスト入力はしない（モバイルでキーボードが出た時点で離脱する）。

**Q1. お住まいは？**
- 戸建て
- マンション・アパート

**Q2. 気になる窓はいくつありますか？**
- 1〜2ヶ所
- 3〜5ヶ所
- 6ヶ所以上

**Q3. 一番気になる窓の大きさは？**
- 小さい窓（トイレ・浴室など）
- 腰高窓（一般的な窓）
- 掃き出し窓（ベランダに出る大きな窓）

質問の合間に、抵抗を潰す一言を小さく添える（「この診断で営業の連絡はしません」「工事は1窓あたり1時間程度です」）。
読ませるのではなく、操作の待ち時間に目に入る位置に置く。

### 結果

**戸建ての場合**: 補助金額の目安をレンジで出す。

補助金額は現行LP（`SubsidyPricing.astro`）に載っている先進的窓リノベの数字をそのまま使う。
新しい制度情報を作らない。

| サイズ区分 | 内窓（Sグレード・戸建） | 対応する選択肢 |
|---|---|---|
| 小 | 22,000円 | 小さい窓 |
| 中 | 34,000円 | 腰高窓 |
| 大 | 52,000円 | 掃き出し窓（下限） |
| 特大 | 76,000円 | 掃き出し窓（上限） |

窓数はレンジの下限×単価下限 〜 上限×単価上限 で計算する。
例: 掃き出し窓・3〜5ヶ所 → 156,000円 〜 380,000円。

**マンション・アパートの場合**: 金額は出さない。

現行LPに載っている補助金額は戸建の数字であり、集合住宅の数字を持っていない。
持っていない数字を推定して出すのは信用を損なうので、
「マンションも対象です。窓の仕様で補助額が変わるため、正確な金額をLINEでお伝えします」として
LINE誘導に繋ぐ。マンション層を取りこぼさず、かつ嘘をつかない。

### 自己負担額の表示

`SHOW_SELF_PAY` フラグで制御する。**初期値は false**。

自己負担額を出すには施工価格のレンジが必要で、これは菊池さんから受け取るまで確定しない。
後から大きく上振れする金額を出すのは、抵抗2を潰すどころか信用を失う。

価格を受け取ったら `src/data/subsidy-estimate.ts` の `CONSTRUCTION_COST` に入れ、
フラグを true にするだけで結果画面に「工事費の目安 − 補助金 = ご負担の目安」が出る。
コンポーネントの改修は不要。

### 結果のコピー

`lin.ee` リンクは友だち追加しかできず、メッセージの事前入力ができない。
そのため結果画面に「この内容をコピー」ボタンを置き、ユーザーがLINEで貼り付けて送る形にする。

コピーされるテキストの例:

```
【窓リフォーム補助金の診断結果】
お住まい: 戸建て
窓の数: 3〜5ヶ所
窓の大きさ: 掃き出し窓
補助金の目安: 156,000円〜380,000円

このプランで見積もりをお願いします。
```

`navigator.clipboard.writeText` を使い、失敗時は `textarea` を使ったフォールバックに落とす
（HTTPSでないと Clipboard API が使えないため。本番はHTTPSだが、ローカル確認で無言で失敗すると気付けない）。

### 状態遷移

```
[intro] 診断開始ボタン
   ↓ start
[q1] → [q2] → [q3] → [result]
   ↑ back（1つ前に戻る）
[result] → やり直す → [intro]
```

進捗バー（1/3, 2/3, 3/3）を出す。3問で終わることが見えていないと途中離脱する。

### 実装単位

- `src/data/subsidy-estimate.ts` — 補助金額テーブル、質問定義、計算ロジック、`SHOW_SELF_PAY` フラグ
- `src/components/subsidy-b/BDiagnosis.astro` — UIとクライアントスクリプト

データとロジックを分離するのは、価格改定のたびにコンポーネントを触らずに済ませるため。
計算ロジックをデータ側に置くのは、金額の出し方が変わったときの変更点を1ファイルに閉じ込めるため。

診断のクライアントスクリプトは、データファイルの内容を `define:vars` でJSONとして受け取る。
Astro の静的出力なのでビルド時に埋め込まれ、追加のフェッチは発生しない。

## 計測設計

`Layout.astro` のクリック委譲は `a` タグの `href` だけを見ているので、
診断のボタン（`button` 要素）は拾われない。診断コンポーネント側で明示的に送る。

| イベント名 | 発火 | 用途 |
|---|---|---|
| `diagnosis_start` | 診断開始ボタン | FVが機能しているかの判定 |
| `diagnosis_q1` 〜 `q3` | 各問の回答 | どこで脱落するか |
| `diagnosis_complete` | 結果表示 | 診断の完走率 |
| `diagnosis_copy` | 結果コピー | LINE送信の意図あり＝最も濃い |

GA4 と Meta Pixel の両方に送る。Pixel は `trackCustom`。

`window.gtag` は本番のみ `Layout.astro` がスタブを定義するが、診断コンポーネントは
`slot` 内にあり Layout の script より先に評価される。順序事故を避けるため、
診断コンポーネント側にも同じスタブを置く（冪等なので重複しても無害）。

`docs/tracking.md` の教訓どおり、`if (window.gtag)` 形式のガードは対象が無いと
エラーも出さずにスキップされる。スタブを自前で持つことでこれを回避する。

`diagnosis_complete` は将来のコンバージョン最適化の候補イベントになる。
電話・LINEタップより発生数が多いはずなので、週50件の学習閾値に届きやすい。

## 画像方針

FVは現行と同じ `case-bedroom-large.jpg` を使うが、**役割を変える**。
現行はFV全面の背景写真で、その上に文字とバッジを重ねている。
B案では診断ウィジェットが主役なので、写真は上部の帯に留めて高さを抑える。

モバイルで「スクロールせずに診断ボタンが見える」ことを最優先にする。

既存のスモークテスト（`scripts/smoke-test.mjs`）がページごとの画像総量を検査するので、
新規ページも予算内に収める。既存画像の再利用のみなので追加圧縮は不要。

## 既存コードへの影響

- `src/pages/subsidy/` は**一切変更しない**。B案が失敗したら広告のリンク先を戻すだけで即復旧できる
- `src/layouts/Layout.astro` も変更しない。既存の `noindex` プロパティで足りる
- 新規追加のみ: `src/pages/subsidy-b/index.astro`、`src/components/subsidy-b/*`、`src/data/subsidy-estimate.ts`
- `SubsidyCases.astro` と `SubsidyTestimonials.astro` はB案からも import して再利用する

## 公開までに必要な確認

コードの完成とは別に、以下は人の判断が要る。

1. **施工価格のレンジを菊池さんから受け取る** → `CONSTRUCTION_COST` に入れて `SHOW_SELF_PAY` を true にする
2. **診断の文言と補助金額を菊池さんが確認する** → 制度の解釈で誤りがないか
3. **B案専用のカスタムコンバージョン2件を追加する**（切り分けたい場合）
4. **広告のリンク先を `/subsidy-b/` に変更する** → 現在キャンペーンは停止中なので、再開と同時に行う

## 検証

- `npm run build` が通ること
- `npm test`（`scripts/smoke-test.mjs`）が通ること。gtag定義・画像予算・フォーマット整合・未参照画像を検査する
- 診断の全経路（戸建3サイズ×3窓数＝9通り、マンション1通り）で結果が出ること
- コピーボタンがローカル（HTTP）でもフォールバックで動くこと
